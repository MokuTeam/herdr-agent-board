# Peer Network для herdr-agent-board — дизайн решения

Статус: черновик на ревью, редакция 2 (по #215). Дата: 2026-10-28.
Репозиторий: `herdr-agent-board` (MokuTeam/herdr-agent-board; `origin` Eithery-rc перенаправляет туда же).
Предыдущая редакция — черновик от 2026-10-27, вне репозитория; расхождения с кодом разобраны в #215.
Issues: сводный #208; этапы #209–#214; риски #215–#221; расход токенов #222.

---

## 1. Задача

Команда — несколько человек (коллеги и друзья). У каждого свой board на своей машине.
Сети разные: разные провайдеры, VPN, NAT, Tailscale у части участников нет и не будет.

Нужно:

1. Видеть, кто из команды сейчас в сети (ростер, как список друзей в Steam).
2. Отправить коллегам список задач — они смотрят свою загрузку и отвечают: беру / не беру / статус.
3. Получать структурированные ответы и статусы, а не переписку в чате.
4. Пригласить человека на сеанс связи (созвон/совместная работа).
5. Не давать пиру возможности управлять чужой машиной.

Явно вне рамок первой версии: голосовые звонки, федерация релеев, общий таск-трекер,
автоматическое принятие обязательств агентами, **агент на приёме входящих** (см. §7.2).

## 2. Ключевые решения

| # | Решение | Почему |
|---|---|---|
| D1 | Один relay-хаб, все борды — клиенты с исходящим соединением | Разные сети и NAT; ни у кого нет открытых портов; presence и ростер появляются бесплатно |
| D2 | Пир не получает HTTP-доступа к борду вообще; входящее от хаба проходит через белый список `kind` в клиенте хаба | Спаренное устройство получает почти весь API борда (см. §3) — это недопустимый радиус; по D1 пир к борду и не подключается |
| D3 | Бродкаст разрешён только для классов `invite` и `offer` | Иначе бродкаст превращается в спам-ленту |
| D4 | Входящее — данные, не команды; в v1 его видит только человек | Правила в промпте не являются границей безопасности; отсутствие агента на входе — является |
| D5 | Коммитит человек, статусы может отдавать агент | Агент не должен наобещать работу |
| D6 | Ответы структурированные (схема), не свободный текст | Иначе нет матрицы «кто что взял» и нет автоматизации |
| D7 | Доставка подтверждается явными состояниями | «Отправил» ≠ «долетело» |
| D8 | Каждое сообщение подписано ключом отправителя; ключи закреплены на бордах | Иначе хаб может подделать любого участника (#217) |
| D9 | Аудит подключений и действий пишется с первого этапа | Нужно отвечать на «кто что отправил и кто принял — человек или агент» (#221) |
| D10 | Всё за ключом `team` в `config.json`; без него — ни одного нового вызова | Установки без функции идут ровно тем же кодом, что раньше (AGENTS.md) |

## 3. Что есть в коде сейчас (main `766ac21`, проверено)

- `GET /api/hello` — идентификация борда: `board: agent-board`, `api` (`REMOTE_API` = 1), `version`, `host`,
  `name`, `dnsName`, `platform`, `remote`; через `tailscale serve` ещё `paired`, `language`.
  На Tailscale-листенере отвечает без токена любому участнику tailnet с разрешённым login.
- `GET /api/peers` — перебор онлайн-нод tailnet и опрос их `/api/hello` на том же порту.
  Только на Tailscale-листенере, только спаренному устройству; tunnel отвечает 404.
  Требует **общего tailnet** — не подходит для нашей задачи. Имя `Peer` в коде уже занято этим.
- `POST /api/remote/pair` + `GET /api/remote/pair/:id` — сопряжение устройства с подтверждением владельца
  (`services/remote.ts`): запрос в памяти, TTL 10 мин, не больше 5 одновременно; токен выдаётся один раз,
  хранится только sha256 в `remote-devices.json`, привязан к Tailscale `node`. Виды: `app` и `browser` (`DeviceKind`).
- `allowedLogin(login, owner, allow)` — кого пускать: владелец или список `remote.allow`
  (у машины, расшаренной тегами, владельца нет — только список).
- `remoteRefusal(raw, path)` (`server/streams.ts`) — что запрещено удалённому вызывающему, в обоих написаниях пути:
  - `desktopOnly` — действия на экране этого компьютера (fs/open, open-url, reveal, focus);
  - `localOnly` — `/api/remote`, `/api/access`, `/api/wake`;
  - всё остальное доступно, а это: сообщения в сессии, answer/permit, restart/wake/sleep/fork,
    `/api/launch` (запуск сессий), `/api/term/*` (терминал), `/api/fs/raw`, `/api/schedule`, `/uploads`.
- Модели ролей в коде нет. Удалённых вызывающих три:
  - **телефон или браузер** через Tailscale (`server/remote.ts`), с токеном спаривания;
  - **tunnel-логин** — из интернета через домен владельца (`server/tunnel.ts`), с cookie входа;
    ему доступен тот же API, что телефону;
  - **desk** — флаг `RemoteDevice.desk` с правом на focus herdr и на approve/deny/revoke спариваний;
    пока только в неслитой ветке `feature/remote-desk`, там же `remoteRefusal(raw, path, desk)`.
- Presence уже есть, но другое: here/away владельца (#172, `core/presence.ts`, `/api/presence`).
- Сквозной список задач — #202 (`feature/todos`, панель Tasks).
- `herdr_relay.py` — **не в этом репозитории** (`dcolinmorgan/herdr-remote`) и не хаб: релей одной машины
  для телефона. Он опрашивает herdr и шлёт состояние всем клиентам, клиенты управляют панелями;
  токен один общий (`HERDR_RELAY_TOKEN`), идентичности клиента нет; офлайн-очереди сообщений нет
  (web-push с collapse, TTL 6 ч). Основой хаба он быть не может (#219).
- В борде нет WebSocket-клиента и кода релея.

Вывод: **роли `peer` нет, и HTTP-роль не нужна**. `device` для нашей задачи слишком широк,
а новые локальные маршруты без явного правила молча откроются телефону, desk и tunnel (§7.1).

## 4. Архитектура

```
                 OVH (relay hub)
        ┌──────────────────────────────┐
        │ registry  presence  queue    │
        │ fan-out   keys      audit    │
        └──────────────────────────────┘
           ▲            ▲            ▲
           │ WSS out    │ WSS out    │ WSS out
      ┌────┴────┐  ┌────┴────┐  ┌────┴────┐
      │ board A │  │ board B │  │ board C │
      │ (Дима)  │  │ (Рома)  │  │ (Слава) │
      └─────────┘  └─────────┘  └─────────┘
```

- Все соединения исходящие, TLS. Ни у кого нет входящих портов.
- Хаб — единственный авторитетный источник состава группы, но не автор сообщений: подпись ставит отправитель (D8).
- Борды не общаются напрямую; всё через хаб.
- **Хаб — новый сервис**: Bun + SQLite, за Caddy на OVH. Код — отдельный репозиторий или `hub/`
  здесь (решить в #209). Резерв — холодный перезапуск из бэкапа SQLite.
- **В борде**: `src/core/team.ts` (схемы и правила), `src/services/team-hub.ts` (исходящий WSS,
  переподключение с backoff по образцу `statusVerdict`), хранилища в stateDir:
  ключ пира, `team-inbox.json`, `team-outbox.json`, журнал аудита.
- Без хаба (недоступен, отозван, выключен) борд работает как раньше; в UI видно состояние подключения.

## 5. Идентичность и доступ

- У пира — постоянный `peer_id` = открытый ключ Ed25519. Секретный ключ — в stateDir
  (0600; на Windows режим не защищает, нужен DPAPI или явное предупреждение).
- Аутентификация на хабе — подпись challenge этим ключом, а не общий токен.
- Инвайт: владелец хаба выдаёт одноразовый invite-код с TTL → новый пир регистрируется → владелец подтверждает.
- Отзыв: удаление ключа из реестра + немедленное закрытие сокета + событие ростера всем. Пир выпадает из ростера сразу.
- Deny-by-default: неподтверждённый пир не видит ни ростера, ни presence.
- Модель ростера: **группа** — все принятые участники видят состав и presence друг друга.
- Закрепление ключей: при первом контакте (TOFU) борд запоминает ключ пира и показывает отпечаток;
  смена ключа — предупреждение, сообщения от нового ключа держатся до подтверждения владельцем.
- Идентичность — у борда, а не у Claude-профиля: несколько профилей и pi на одной машине — один пир.

## 6. Протокол

### 6.1 Конверт

```json
{
  "v": 1,
  "id": "uuid",
  "from": "peer_id",
  "to": "peer_id | *",
  "kind": "invite | offer | response | status | question | data | ack",
  "reply_to": "uuid | null",
  "ts": "iso8601",
  "ttl_s": 86400,
  "body": { },
  "sig": "ed25519(from, все поля выше)"
}
```

`presence` — не конверт, а событие хаба по отдельному каналу (никто из пиров его не шлёт).
`v` — версия протокола; борд отклоняет неизвестную старшую версию с понятной ошибкой.

### 6.2 Классы сообщений

| kind | `to: *` | Подтверждение | Кто может отправить | Назначение |
|---|---|---|---|---|
| `invite` | разрешён | получатель принимает/отклоняет | человек | приглашение на сеанс |
| `offer` | разрешён | обязательное, с дедлайном | человек | список задач |
| `response` | — | не требуется | человек | ответ на offer |
| `status` | — | не требуется | человек или агент (только по своим принятым пунктам) | статус по принятой задаче |
| `question` | запрещён | обязательное | человек | точечный вопрос |
| `data` | запрещён | обязательное | человек | передача данных |
| `ack` | — | не требуется | борд | подтверждение доставки/обработки |

Событие хаба `presence` (онлайн/офлайн) — вне таблицы, см. §6.1.

### 6.3 Состояния доставки

Транспорт: `queued → delivered → acked`, либо `expired`.

- `queued` — принято хабом, получатель офлайн, лежит до TTL
- `delivered` — сокет получателя принял
- `acked` — борд получателя проверил подпись и записал сообщение
- `expired` — TTL вышел до `acked`; отправитель получает уведомление

Прикладное состояние `replied` (есть `response`/`status` с этим `reply_to`) показывается из нити,
транспорт его не знает.

Идемпотентность по `id` на хабе и на борде; повторная отправка того же `id` не создаёт дубль.
Ретраи с экспоненциальной задержкой.

### 6.4 Body: offer

```json
{
  "title": "Задачи на неделю",
  "reply_by": "2026-10-28T18:00:00Z",
  "items": [
    {"n": 1, "title": "Починить экспорт", "priority": "P1", "estimate_h": 2, "ref": "142"}
  ]
}
```

Пункт адресуется ключом `(from, offer_id, n)`, а не глобальным `task_id`: общего трекера нет,
коллизий так не бывает. `ref` — необязательная ссылка на задачу у отправителя (Beads, Tasks #202).

### 6.5 Body: response

```json
{
  "answers": [
    {"n": 1, "verdict": "accept", "eta_h": 3, "comment": ""}
  ],
  "load": {"active_tasks": 2, "hours_in_flight": 6}
}
```

`verdict`: `accept | decline | defer | clarify`.

## 7. Безопасность и радиус поражения

### 7.1 Граница: клиент хаба, не HTTP-роль

Пир к борду не подключается (D1), поэтому HTTP-роли `peer` нет. Граница — в клиенте хаба:

- белый список `kind` → обработчик; неизвестный `kind`, неверная подпись или незакреплённый ключ — отброс и запись в аудит;
- каждый обработчик только пишет в `team-inbox.json` и шлёт SSE-событие; **ни один не вызывает herdr, launch или term**
  (тест с моком herdr).

Владелец работает с сетью через локальные маршруты **`/api/team/*`** (ростер, входящие, нити, отправка, ответ).
Имя не `/api/peer*`: рядом `/api/peers`, и regex `localOnly` легко захватит лишнее.

Правило для удалённых вызывающих (решается в #218, до #210):

| Вызывающий | Чтение `/api/team/*` | Ответ на offer/invite | Отправка offer/question/data |
|---|---|---|---|
| Локальный борд | да | да | да |
| Телефон или браузер (Tailscale) | да | да | нет |
| desk | да | да | нет |
| tunnel-логин (интернет) | да | да | нет |

Отказы реализуются по образцу `DESK_REMOTE_OPS` (`feature/remote-desk`): проверка op для `/api/team`,
оба написания пути. Порядок слияния с `feature/remote-desk` согласовать.

### 7.2 Входящее и агенты

- **v1: входящее видит только человек.** Оффер, вопрос, приглашение — карточка на борде;
  ни в одну сессию и ни в один терминал не попадают.
- «Приёмной сессии» в v1 нет. Ограниченного профиля для сессий в лаунчере нет (`core/launch/*`
  не передаёт allowedTools/permission-mode), а ограничения Claude Code — политика процесса, не граница ОС.
- Если агент на входе понадобится позже: только метаданные (кто, тема); тело — с меткой `untrusted`;
  отдельный OS-пользователь или sandbox; из инструментов — только `board team reply`. Отдельный дизайн (#216).

### 7.3 Исходящее от агента

- Агенту доступен только `board team status <offer>/<n> "<текст>"` по пунктам, **принятым на этом борде**.
  `data`, `question`, `offer` отправляет только человек.
- Источник (`agent`/`human`) ставит борд по пути вызова (CLI из сессии или UI), а не берёт из тела.
- Лимит длины и частоты; вложений нет; простая проверка на секреты (`sk-…`, `ghp_…` и т. п.)
  с отказом без подтверждения человеком (#220).

### 7.4 Квоты

- N сообщений в час на пира — на хабе и на борде.
- Один активный offer от отправителя к получателю. Бродкаст offer при уже активном offer
  к кому-то из получателей не доходит до этого получателя, отправитель видит это в матрице.

### 7.5 Шифрование

- P0–P4: TLS до хаба + подписи отправителя (D8). Хаб видит тела, но не хранит их после `acked`
  (по умолчанию; настраивается).
- P5: E2E — шифрование на каждого получателя (X25519 + AEAD), при `to: *` — на каждого из ростера;
  ключи берутся из закреплённых (§5), иначе хаб может подменить ключ (MITM).

## 8. Модель данных (хаб)

```
peer(id, public_key, display_name, status, last_seen_at, created_at, revoked_at)
invite(code, created_by, used_by, expires_at)
message(id, v, from_peer, to_peer, kind, reply_to, state, created_at, expires_at, size, body_hash, payload, sig)
presence_event(peer_id, state, at)
audit(seq, prev_hash, peer_id, action, detail_json, at)
```

- `payload` — непрозрачный для хаба; удаляется после `acked` (по умолчанию). В P5 — шифртекст.
- Таблиц `offer`/`response` на хабе нет: офферы и ответы — забота бордов.

## 9. Аудит (#221)

Запись — с P0, экран — P5. Журнал только дописывается; каждая запись хранит хеш предыдущей.

**Хаб:** подключение и отключение (`peer_id`, IP, версия клиента, причина), инвайт выдан/использован,
подтверждение, отзыв; каждое сообщение без тела (`id`, from, to или `*` с числом получателей, `kind`,
размер, хеш тела) и его переходы состояний; отказы (бродкаст запрещённого класса, квота, подпись, `kind`).

**Борд:** входящее и что с ним сделал человек; исходящее и его источник — `human` (с какого входа:
локально, телефон, tunnel) или `agent` (какая сессия и панель); отказы проверки на секреты; отброшенные входящие.

Читают: владелец хаба — журнал хаба; участник — свои записи; владелец борда — локальный журнал.
Хранение — 90 дней по умолчанию, без тел и без секретов. Без ключа `team` журнал не создаётся.

## 10. Расход токенов (#222)

Передача данных — хаб, ack, очередь, ростер, presence, карточки, матрица — **0 токенов**.

| Место | Тратит? | Порядок |
|---|---|---|
| Транспорт, ростер, показ оффера человеку | нет | 0 |
| Агент шлёт статус (P4) | да, внутри идущей сессии | ≈ 200–500 на вызов |
| Агент составляет оффер по просьбе человека | да | разово ≈ 1–3k |
| Строки о сети в hook-контексте сессий | **запрещено** | было бы ≈ 50–200 × каждый промпт каждой сессии |
| «Приёмная сессия» | нет в v1 | было бы ≈ 15–30k (с кэшем) на каждое входящее |

Число вызовов агента на сообщение пишется в аудит (§9) и видно на экране P5.

## 11. UX

- **Ростер**: список участников, точка online/offline, last seen, отпечаток ключа, кнопка «пригласить на сеанс».
  По желанию — here/away из существующего presence (#172).
- **Оффер**: карточка со списком задач, дедлайн ответа, подсказка о собственной загрузке,
  кнопки «Возьму / Возьму всё / Не возьму / Уточнить». Кнопку жмёт человек.
  Принятые пункты попадают в Tasks (#202).
- **Матрица ответов** у отправителя: кто взял что, кто молчит, что просрочено, кому offer не дошёл из-за квоты.
- **Статусы**: от агента принявшего или от человека, с источником (`agent`/`human`).
- **Состояние подключения** к хабу: подключено / переподключение / отозвано / выключено.

## 14. Критерии приёмки

- Пир видит ростер и presence, не имея доступа ни к одному эндпоинту чужого борда (у пира нет HTTP-доступа вообще).
- Сообщение, отправленное офлайн-получателю, доставляется после его подключения и имеет состояние `acked`.
- Входящее любого `kind` не приводит ни к одному вызову herdr, launch или term (тест).
- Сообщение с неверной подписью или от незакреплённого ключа отбрасывается и попадает в аудит.
- Бродкаст класса `question`/`data` отклоняется хабом.
- Отозванный ключ перестаёт работать немедленно (сокет закрыт меньше чем за 1 с), и пир исчезает из ростера.
- Агент не может отправить `data`/`question`/`offer` и статус по непринятому пункту.
- Без ключа `team` поведение борда, хуков и remote/tunnel-листенеров совпадает с main (тест; сравнение в PR).
- По журналу аудита восстанавливается, кто был онлайн и кто кому что отправил; правка задним числом обнаруживается.
